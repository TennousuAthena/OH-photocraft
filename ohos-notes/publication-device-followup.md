# URI publication device follow-up

On 2026-10-08, package #5 displayed `Invalid argument` after a new-target PSD Save As. The editor remained dirty. Its external target's content had not yet been verified, and the captured app-tag log was empty, so the complete provider publication path must not be recorded as passed.

In the same package, title-bar Close → Cancel kept the application open. A later Close → Save displayed `File exists` and kept the unsaved prompt and dirty document. The publication root was recreated with recursive `mkdir` on every save, although that SDK call can reject an already existing directory. Import/recovery/binding directories now use a shared create-or-check policy: inspect each sandbox ancestor with `lstat`, create missing children with single-level `mkdir`, accept a concurrent `13900015` only after verifying the created object, and require every ancestor to be a real directory rather than a symlink or file. The folder import helper already used existence checks and ordinary-directory validation.

Source review found that the recovery job used `fileIo.mkdtemp(... + '/publication-')`, before entering the backup/write/rollback transaction. The official CoreFileKit contract requires a template ending in `XXXXXX`; the native implementation passes it directly to `uv_fs_mkdtemp`. The call is now `publication-XXXXXX`. The unconnected folder import helper had the same template omission and was corrected too. This fixes a definite API contract violation that matches the observed error location; the next device build must verify the actual outcome and all subsequent provider operations.

Evidence: [official mkdtemp contract](https://github.com/openharmony/docs/blob/master/zh-cn/application-dev/reference/apis-core-file-kit/js-apis-file-fs.md#fileiomkdtemp), [official native implementation](https://github.com/openharmony/filemanagement_file_api/blob/master/interfaces/kits/js/src/mod_fs/properties/mkdtemp.cpp). Node's public `fs.mkdtemp(prefix)` appends random characters itself; it therefore cannot stand in for the CoreFileKit template call without an explicit adapter. macOS libc is also more permissive about templates than the HarmonyOS contract.

Fixed-stage diagnostics now distinguish picker/prepare/publication completion and the recovery-root/job creation boundary. SDK storage diagnostics identify open, copy, truncate, seek preflight, journal write/rename, file fsync, and directory fsync. Only the fixed stage and numeric error code are logged; no URI, filename, sandbox path, or document text is included. SDK error `13900020` may arise from copy, seek, truncate, or fsync, so a later provider failure must be located from its actual stage rather than by weakening those checks.

Eight additional host regressions exercise the production `DocumentBridge` and `PublicationFileStorage` over real temporary files with a shim that enforces the documented SDK FD/template contract. They cover native unique-directory creation with a valid template, a new empty target, repeated publication with an existing recovery hierarchy, rejection of file and symlink ancestors, seek rejection before mutation, journal directory sync rejection before destination-write opening, and partial-copy failure restoring old bytes while still rejecting Save. These are host contract checks, not proof of any particular external provider's capabilities. Together with the existing transaction, folder, and paste authorization suites, 55 ArkTS-side host tests pass.

The backup, durable journal, no-TRUNC preflight, write/fsync, and same-live-descriptor rollback policy remain intact. This is a recoverable publication transaction, not atomic saving across providers. Device acceptance must still cover the new-target Save As, overwrite, interrupted publication recovery notice, and provider rejection of read/seek/truncate/copy/fsync without an incorrect clean-document acknowledgement.
